# token-inbox 每日编号与保险箱清理重设计

日期：2026-10-17
状态：已确认（用户逐条拍板）

## 背景与问题

现实现（`hooks/register.ts`）：

- 入箱编号为全局自增整数（`第N个`），上限 100，满了 FIFO 淘汰最旧；
- `vault-apply` 的 `index` 缺省回退到 1；
- `/token-flush` 手动清空。

由此产生两类错误：

1. **静默写错值**：模型漏传 `index` 时默认落 `token:1`——会话内有多个 token 时，
   写入目标文件的是错误的 token，且返回成功消息，无任何报警。
2. **FIFO 淘汰后悬空引用**：占位符（`第N个`）留在不可改写的会话历史里，`token:N`
   被淘汰后模型调 `apply(N)` 只得到"保险箱里没有这个 token"，不说明原因、不列出可用
   编号，诱导模型换编号重试 → 回到问题 1，错误的值被写进文件。

根因是**语义层**的：不可变历史占位符 ↔ 可淘汰存储之间的悬空引用，加上 apply 侧
校验过于宽松。与存储引擎无关——评估过引入 sqlite，结论是不解决根因（事务/自增/
墓碑表都不改变悬空引用本身），且原生依赖（better-sqlite3 需编译、node:sqlite 需
Node ≥22.5）对 hooks 插件是脆弱性净增加，弃用。

## 设计

### 编号格式

- `YYYYMMDD-NNN`，3 位定宽补零，如 `20261017-001`；
- 每日从 001 起，当天内只增不复用（`nextN` = 当天既有编号 max + 1）；
- 定宽保证**纯字符串排序 = 时间序**（日期定宽 + 序号定宽），FIFO 与排序无需拆字段；
- 日期前缀隔离键空间：跨天编号重置不会与旧键冲突；编号不再无限增长；
- 占位符形如：`[token-inbox:20261017-001已入箱脱敏;需要落值时调用vault-apply并传此编号]`；
- 旧格式占位符（纯数字）无迁移问题：apply 时命中格式校验报错，旧会话可感知。

### 入箱（prompt.submit 处理带 token 消息）

1. 解析 TOKEN_RE 命中后：
2. **去重**：仅当天范围内查重，同一真值引用既有编号；跨天重发同一真值 → 入新编号
   （语义自洽，接受）；
3. **新值入箱**：编号 = 当天 max + 1；
4. **全箱 FIFO**：入箱后若全箱键数 > 1000，按字符串升序（即时间序）淘汰最旧，直到
   ≤ 1000。不写墓碑、不区分"曾存在"——淘汰后查不到就是没有；
5. **单日超限**：当天已有 1000 个、又出现新真值 → 不入箱，走 fail-closed 整体拦截，
   drop 理由：
   `token-inbox：今日脱敏额度已满（1000），信息脱敏不可用；请执行 /token-flush 清空保险箱后重试`

### 落值（vault-apply 严格化）

`index` 参数类型改为 string（模型从占位符原样复制，如 `"20261017-001"`）：

1. **宽松解析**：`YYYYMMDD-N` 形式的短序号自动补零为 NNN；
2. **index 省略**：仅当箱内恰好 1 个 token 才落地；否则报错并列出可用编号（规则同下）；
3. **编号存在** → 落地，行为同现状（写 `KEY=value` 一行，返回只含长度不含明文）；
4. **编号不存在** → 报"编号不存在；可用编号：…"。可用编号列表最多列 20 个（当天
   优先，按时间序），超出以"…等 N 个"收尾；并明确提示**禁止改用其他编号落值**，
   应请用户重发该 token；
5. **格式不对**（含旧格式纯数字）→ 报"编号格式应为 YYYYMMDD-NNN"并列出可用编号、禁止改用——不给具体示例编号，防止模型照抄示例造成写错值。

### /token-flush（恢复用途，回归）

- 定位改变：**不是**日常维护入口，正常流程永远用不到；唯一用途是单日额度满、或
  保险箱异常时的手动恢复，报错文案直接指路；
- 行为：清空全部 `token:*`，返回删除计数；清空后当天编号重新从 001 起；
- 已知接受项：清空前的旧占位符在同一天内会指向新入箱的值（编号复用）。flush 是
  显式用户动作且模型上下文可见其结果，与原设计一致。

### 自动清理

- 仅一条规则：**1000 键全局 FIFO**（见入箱第 4 步）；
- 无按日期清扫、无墓碑、无定时任务；
- 存储占用上界：1000 键 × ~70B ≈ 70KB，远低于 `$.store` 的 4MiB 硬上限。

### 已知边界（明确不处理）

- 单日超过 1000 个新真值：报错拦截（见上），不写任何绕过代码；
- 若单日灌满导致编号超出 `NNN` 三位：依赖上一条报错挡住，不会实际发生；
- 跨真实午夜的场景（会话跨天、清理时机）不做专门测试。

## 测试计划

改造现有用例：

- 占位符断言 `第1个`/`第101个` → `YYYYMMDD-NNN` 新格式；
- 去重用例：当天内引用 `-001`；
- flush 用例：清空后同 token 重新从 `-001` 编号。

新增用例：

1. 单日超限：灌满当天 1000 个后再发新 token → drop，消息含"/token-flush"；
2. 全箱 FIFO：淘汰逻辑抽为纯函数（输入全箱编号集合与上限，输出待淘汰列表），直接
   单测"跨日按字符串序淘汰最旧、总数守恒"。不走事件级测试——同日灌满会先触发单日
   超限拦截，事件级构造 >1000 键需要真实跨日时钟，不值得为此引入时钟注入；
3. apply：省略 index 且箱内多 token → 报错列可用编号；
4. apply：省略 index 且箱内唯一 token → 落地；
5. apply：编号不存在 → 报"不存在 + 可用编号列表"；
6. apply：旧格式纯数字 → 报格式错误；
7. apply：短序号 `-1` 补零命中 `-001`。

不测：跨真实午夜的入箱/清理。

## 不做的事

- 不引入 sqlite（理由见背景）；
- 不做墓碑/淘汰元数据（查不到就是没有）；
- 不做按日期的主动清扫；
- 不做编号格式版本迁移（旧会话占位符靠格式校验报错自然感知）。
